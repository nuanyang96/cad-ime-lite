## 1. 问题

v5 在虚拟机（微信输入法 3.0.1.12）里无效：
- CAD 命令行敲 `abc` 出中文候选；
- 日志：`11:20:20.171 判据=绘图区(MDIClient)→英文 目标=英 conv 0x0001->0x0000 OK`，之后全是 `conv 0x0000->0x0000 OK`。
搜狗 16.9.0.5535 实测同样现象（`conv 0x0401->0x0000 OK` 之后 `0x0000->0x0000`）。

## 2. 根因（实测确认，两次独立验证）

- **转换模式通道对这两家无效**：`IMC_SETCONVERSIONMODE` 设 0，读回 0，**敲字仍是中文候选**
  （探针截图 `crop_P2_conv0.png`：设完 0 后敲 xyz，出的是"小姨子/心眼子"等中文候选）。
  v5 就是被"读回 0"骗了，以为已经切成英文，之后不再动作。
- 微软拼音走同一条通道是有效的，必须保留。

## 3. TSF 通道：核实结论是不可行（探针实测，不再尝试）

在虚拟机 session 1（交互桌面）用 `TsfProbe.exe` 实测：

| 检查项 | 结果 |
|---|---|
| `CoCreateInstance(CLSID_TF_ThreadMgr)` + `Activate` | 成功（tid=32） |
| `GetGlobalCompartment` → `ITfCompartmentMgr` | 成功 |
| `ITfCompartment` 槽位自检（写 777 回读 777） | 通过（SetValue=槽3 / GetValue=槽4） |
| 全局 compartment 表 | 空的，没有任何 conversion / openclose 项 |
| 原子表里 29 个 compartment GUID 逐个 GetValue | 全部 `S_FALSE`（外部进程读不到值） |
| `ITfThreadMgr` QI 到 `ITfCompartmentMgr` | 不支持（AA80xxxx 段 65536 个 IID 全部扫过） |

结论：两家输入法的中英状态存在**目标进程自己的 TSF context** 里，外部进程拿不到；
除非往 acad.exe 注入 DLL，风险不接受，本次不做。

## 4. 真正可用的通道：输入法开/关（IMM32 IMC_SETOPENSTATUS）

实测（虚拟机，CAD 命令行，v6 日志 `通道=imm32open`）：

- 设 **关** → 敲 abc 出 `abc`（拉丁字母）→ 英文
- 设 **开** → 敲 xyz 不出拉丁字母（进入中文组合）→ 中文
- 读回值与设置一致，托盘指示器同步显示 中/英

所以 v6 把"落地"改成三条通道，按 rules.ini 的 `channel=` 选择：

1. `imm32conv`：转换模式（微软拼音）
2. `imm32open`：**开/关**（微信输入法 / 搜狗，实测有效）
3. `shift`：合成一次 Shift（兜底；带 `WH_KEYBOARD_LL` 钩子识别用户手按 Shift，不覆盖用户操作）
4. `tsf`：保留代码但默认不启（需要 `tsf_guid=`，本次无可用 GUID）

`auto` 的选择方式：**按输入法身份判定，不靠"设了再读回"试错**（读回值会骗人，见第 2 节）。

- 先看目标进程（acad.exe）里加载了哪些 IME 模块：命中 `wetype` → 微信输入法，命中 `sogou` → 搜狗，
  命中 `qqpy/qqpinyin` → QQ 拼音，命中 `baidu*/weasel/rime` → 对应输入法；
- 命中第三方中文输入法 → 走 `imm32open`（开/关）子通道；
- 命中微软拼音（或不含第三方 IME 模块）→ 走 `imm32conv`（转换模式）子通道；
- 进程模块和 `ImmGetDescription`/`ImmGetIMEFileName` 都读不到 → 按 `conv → open → shift` 顺序回落，
  日志里写明 `auto未识别IME=`，方便下次补名单；
- 日志每次都带 `IME=<名字>`（识别不到写 `IME=未识别`）。

判断依据为什么是"进程模块"：实测微信输入法在 acad.exe 里加载了 `wetype_tip.dll` 和
`wetype_tip_core.dll`；而 `ImmGetDescription`/`ImmGetIMEFileName` 对本机的 TSF 输入法返回空
（探针实测 `hkl=0x8040804 descLen=0`），单靠这两个 API 认不出来。

## 5. MTEXT 判据：LSP 通道（本次新增依赖）

AutoCAD 的在位 MTEXT 编辑器**没有任何窗口特征**（实测：焦点窗口与绘图区同一个 hwnd、类名相同、
`hwndCaret=0`、主框架与 0x307DE 的子窗口在编辑态和空闲态完全一致），所以窗口判据无法区分"命令输入"和"多行文字编辑"。

因此中文判据改由 LISP 提供（v5 代码里本来就留了这条通道）：

- LSP 用命令反应器，在 MTEXT/MTEDIT/DDEDIT/TEXTEDIT/TEXT/DTEXT 等命令**开始时**写
  `HKCU\Software\CadImeSwitch` 的 `Line3=CN`、`Command=<命令名>`；
- 命令结束/取消/失败写 `Line3=IDLE`（= 英文）；
- CadImeLite 读 `Line3`：`CN` → 中文，`EN`/`IDLE` → 英文，日志里记 `判据=LSP(CN)` / `判据=LSP(IDLE)`。

**这份 LSP 与主机 `C:\CadImeSwitch\CadImeSwitch.lsp` 是同一份文件**（SHA256
`45C6520C17DAD4ED10EBBEBA93FF1055A7AD8F096901D314002BA2913FE6BBA6`），主机不需要改任何东西；
虚拟机原来没装，本次补装。

## 7. rules.ini 新增

```ini
channel=auto      # auto / imm32 / conv / open / shift / tsf
tsf_guid=         # 留空；只有确认某输入法开放 compartment 时才填
```

交付值就是 `channel=auto`（交付对象是主机、主机是微软拼音，auto 会按身份落到 `imm32conv`）。
虚拟机（微信输入法）上 auto 实测落到 `imm32open`，日志：`IME=微信输入法 通道=imm32open`。

## 9. 已知限制（如实记录）

1. `shift` 通道是盲切（没有可靠读数），只在 `auto` 且前面通道都失败时才会用到。
2. **`open` 通道是"关输入法"，不是"改模式"**：关掉后敲字母直接进程序（等于英文），但
   用户手按 Shift **不会有反应**（跟转换模式下的 Shift 行为不同）。主机的微软拼音走 conv 通道，
   不受这一条影响；只有微信/搜狗这类落到 open 通道的输入法才是这个行为。
3. **虚拟机与主机的加载方式不同**：
   - 虚拟机：注册表启动组键值写了但 **CAD 不加载**（键值在、CAD 不跑），实际靠
     `AutoCAD 2024\R24.3\chs\Support\acaddoc.lsp` 每次开图形加载；
   - 主机：走启动组（2024 `4Startup`、2018 `3Startup` 都指向 `C:\CadImeSwitch\autoload.lsp`）。
   - **主机上不要去动 acaddoc.lsp**：2026-10-24 主机那两份曾被金山毒霸改名成 `.disabled`，
     动它会把整条 LSP 链路搞断。这是已知差异，也是风险点。
4. 依赖 LSP 提供 MTEXT 判据：LSP 没加载时，MTEXT 仍会被判成英文（退化成 v5 的已知代价）。
5. `auto` 的 IME 识别靠模块名匹配，名单外的输入法会走"未识别"回落（conv→open→shift），
   日志里能看出来，补名单即可。

## 10. v6.1 修正（2026-10-28 主机冒烟后）

1. **不再做"设了再读回"的通道判决**。原逻辑在 `#32770` 对话框里读到"设中文读不回来"，

   `conv 0x0401->0x0000 OK`，说明读不回来是**那个窗口**的特性，不是 IME 能力。

   conv 失败只写 `通道=imm32conv 未生效（本窗口读不回来，不换通道）`，绝不切 open。

## 13. v6.4：单实例保护 + 日志带进程号（2026-10-28）

现场问题：主机上同时跑过 3 个实例（自启项 + switch 脚本各 start 一次 + 手工双击），
三个托盘图标、三份日志、三个实例互相抢 IME 状态。

改动：
1. **单实例互斥体**：启动先 `new Mutex(true, "Global\CadImeLite.SingleInstance")`，
   拿不到就写一行 `已有实例在跑（互斥体 …），本进程退出` 然后直接退出，不弹窗；
   `Global\` 建不了（权限）自动退到 `Local\`。进程退出时 `ReleaseMutex` + `Dispose`。
2. **日志带进程号**：每条日志前面加 `[pid:12345]`，多实例（或旧版残留）同时写时一眼能分开。
3. **switch-to-v6.cmd 加等待**：taskkill 之后轮询 `tasklist` 最多 5 次确认进程真的没了才 copy+start，
   避免"杀掉没生效就 start 出两个"。

## 14. v6.5：托盘图标改成运行时画「中 / 英」（2026-10-28）

现象：主机 v6.4 托盘位置是空白方块，韩工看不到 中/英；v5 时能看到。

定位：**代码里从来没有画过 中/英**——v4/v5/v6 一直用的都是 `icon.Icon = SystemIcons.Application`
（通用应用图标），没有"中/英"字样。所以"v5 能看到中/英"应该是任务栏那个**输入法指示器**，
不是这个托盘的图标；托盘那个位置从 v5 起就是通用图标，v6.4 在主机上显示成空白方块，
属于 Windows 通知区域图标的显示/缓存问题，不是 v6.0→v6.4 之间的代码回退（这段代码没动过）。

改法（v6.5）：不再依赖系统图标，运行时用 GDI+ 画 32×32 色块 + 白字：
- 中文：「中」，红底 `#C02020`
- 英文：「英」，蓝底 `#2060C0`
- 状态变化时（Tick 判定后、离开 acad 复位后）调用 `SetTrayState()` 换图标，并更新托盘提示文字
- `Icon.FromHandle` 之后 `Clone()`、随即 `DestroyIcon`，旧图标在换掉后 `Dispose`，不泄漏

v6.5 版本：`CadImeLite.exe` 44,032 字节，SHA256 `864985316BE42BB0563ABE15FCA1D4298851B73E35A3231CE41C13EE04ED9EAA`。
